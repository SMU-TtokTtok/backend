# 동아리 조회수 동시성 — 처리 방식별 트레이드오프 실측

이슈 [#346](https://github.com/SMU-TtokTtok/backend/issues/346)

## 요약

동아리 상세 조회의 조회수 증가가 read-modify-write 라서 동시 요청에서 증가분이 유실된다.
**100 VU / 5,000 요청 조건에서 조회수의 90.14% 가 유실됐다** (5,000건 중 493건만 반영).

원자적 UPDATE 로 바꾸면 유실이 0이 되고, **처리량은 오히려 1.93배 늘었다** (RPS 311.7 → 601.4).
정확성과 성능이 같은 방향으로 개선되는 경우다.

단, 원자적 UPDATE 안에서도 **문장 순서가 처리량을 1.84배 가른다**. 이게 이번 측정의 핵심 발견이다.

## 측정 조건

| 항목 | 값 |
|---|---|
| 부하 | 100 VU, 5,000 요청 (shared-iterations, think time 없음) |
| 대상 | `GET /api/clubs/{clubId}/content` (단일 동아리 행에 집중) |
| 경로 | k6 → nginx → app → PostgreSQL (모두 컨테이너) |
| 리소스 | app 2 vCPU / 2GB, db 2 vCPU / 1GB, HikariCP max-pool-size 10 |
| 워밍업 | 매 측정 전 2,000 요청 (결과 폐기) |

유실 판정은 psql 로 한다. `view_count` 는 어떤 API 응답에도 노출되지 않기 때문이다.
기준값은 설정한 iterations 가 아니라 **k6 가 실제로 받은 2xx 응답 수**다 — 실패한 요청은 조회수를 올리지 않으므로,
iterations 로 계산하면 유실을 과대평가한다.

## 결과

| 변형 | 유실 | 실패율 | RPS | p50 | p95 | p99 | max |
|---|---|---|---|---|---|---|---|
| V0 현행 (read-modify-write) | **90.14%** | 0% | 311.7 | 300.1 | 481.5 | 622.4 | 1091.1 |
| V1a 원자적 UPDATE — 증가 먼저 | 0% | 0% | 327.3 | 296.3 | 371.4 | 406.8 | 738.8 |
| **V1b 원자적 UPDATE — 증가 마지막** | **0%** | **0%** | **601.4** | **157.5** | **244.8** | **325.0** | **479.1** |
| V1c 원자적 UPDATE — 트랜잭션 미사용 | 0% | 0% | 319.4 | 299.2 | 472.5 | 586.0 | 823.8 |
| V2 낙관락 (@Version, 최대 3회 재시도) | 0% | **67.36%** | 150.8 | 699.6 | 1011.5 | 1205.1 | 1779.1 |
| V3 비관락 (SELECT … FOR UPDATE) | 0% | 0% | 245.9 | 401.1 | 480.7 | 503.6 | 517.4 |

**채택: V1b.** 정확성 100% 에 처리량·지연 모두 최고이며, 스키마 변경이 필요 없다.

## 해석

### 원자적 UPDATE 도 락을 쓴다 — 문제는 "얼마나 오래 쥐느냐"

`UPDATE ... SET view_count = view_count + 1` 은 무락이 아니다. 행 배타 락을 잡는다.
그리고 **PostgreSQL 은 행 락을 문장 종료가 아니라 커밋까지 유지한다.**

- **V1a (증가 먼저)**: 락 보유 = UPDATE + 상세 조회 2쿼리 + 커밋
- **V1b (증가 마지막)**: 락 보유 = UPDATE + 커밋

같은 "원자적 UPDATE" 인데 RPS 327.3 vs 601.4 로 1.84배 차이가 났다. 단일 핫 로우의 처리량 상한은
대략 `1 / 락 보유 시간` 이므로, 임계 구간에 읽기를 끌어들이는지가 그대로 처리량에 반영된다.
그래서 V1b 는 조회 결과로 존재 여부를 판정하고(부수적으로 null 방어가 명시적이 된다) 증가를 맨 뒤에 둔다.

### 트랜잭션을 없앤다고 더 빨라지지는 않는다 (V1c)

락 보유를 더 줄이려고 `@Transactional` 을 떼고 증가만 자체 트랜잭션으로 돌렸더니 RPS 319.4 로 오히려 V1b 의 절반이었다.
리포지토리 호출마다 커넥션을 새로 얻고 커밋이 한 번 더 붙는 비용이, 짧아진 락 보유 이득을 넘어선다.
풀 크기가 10인 환경에서는 커넥션 획득 자체가 비싸다.

> `REQUIRES_NEW` 로 증가만 분리하는 방식은 아예 시도하지 않았다. 요청당 커넥션 2개를 동시에 점유해
> 풀 고갈 데드락을 만든다.

### 낙관락은 이 워크로드에 정면으로 부적합하다 (V2)

조회수는 **모든 요청이 같은 행을 쓰는 충돌률 100% 워크로드**다. 낙관락은 충돌하면 이미 한 일을 버리고 다시 하므로,
충돌률이 올라갈수록 유효 처리량이 역주행한다.

- 5,000 요청 중 **1,632 건만 성공, 67.36% 가 실패**(3회 재시도 소진 후 500)
- 재시도 로그 **16,297 회** (attempt=1: 6,134 / attempt=2: 5,414 / attempt=3: 4,749)
- 1,632 건의 조회수를 반영하려고 16,297 개의 트랜잭션을 버렸다

"성공한 요청만 보면 유실 0%" 라는 점에 속으면 안 된다. 사용자 입장에서는 셋 중 둘이 에러다.

### 비관락은 정확하지만 읽기까지 직렬화한다 (V3)

정확성은 V1b 와 같고 실패율도 0이다. 지연 분포는 오히려 가장 좁다(p50 401 → max 517).
줄을 세우니 예측 가능해지는 것이다. 대신 처리량이 245.9 로 V1b 의 41% 에 그친다.

이유는 MVCC 다. 행 배타 락은 **읽는 쪽을 막지 않으므로** 상세 조회 쿼리들은 원래 락 대기 없이 병행된다.
`SELECT ... FOR UPDATE` 로 시작하면 그 병행성을 스스로 포기하고, 왕복도 한 번 더 든다.

## 선택 기준

이 결과를 "원자적 UPDATE 가 빠르다" 로 요약하면 다음 이슈에서 잘못 적용하게 된다. 기준은 **무엇을 보호해야 하는가** 다.

- **블라인드 증가 — 현재 값을 읽고 판단할 필요가 없는 쓰기 → 원자적 UPDATE**
  조회수가 여기 해당한다. 읽을 필요가 없으니 읽기를 보호할 락도 필요 없다.
- **읽은 값으로 분기해야 하는 쓰기 → 비관락이 정당하다**
  지원 정원 체크(`maxApplyCount`)처럼 "현재 인원을 읽고 미달이면 insert" 는 읽기-판단-쓰기가 원자적이어야 하고
  한 문장으로 접을 수 없다. 조회수의 결론을 그대로 가져가면 안 되는 사례다.
- **충돌률이 낮고 트랜잭션이 긴 경우 → 낙관락**
  조회수는 정반대 조건이었고, V2 수치가 그 대가를 보여준다.

## 측정하지 않고 결론만 남기는 항목

- **인덱스**: 이 이슈의 해법이 아니다. 쓰기 경로의 `WHERE id = ?` 는 PK 조회라 이미 인덱스가 있고,
  추가할 여지가 없다. 인덱스는 탐색 비용을 줄이지 경합을 줄이지 않는다.
- **Redis 카운터 / 샤딩 카운터**: 단일 핫 로우 쓰기는 어떤 방식이든 결국 직렬화되므로 V1b 에도 상한이 있다.
  그 상한을 넘겨야 한다면 다음 수는 비관락이 아니라 카운터를 DB 밖으로 빼거나 행을 N개로 쪼개 합산하는 방향이다.
  최종적 일관성과 장애 시 유실을 감수하는 트레이드오프이므로 별도 판단이 필요하다.

## 측정 신뢰도에 대한 유의사항

**콜드 스타트를 반드시 배제해야 한다.** 이번 측정에서 가장 크게 데인 부분이다.
컨테이너 재기동 직후 첫 실행은 JIT 미컴파일·빈 커넥션풀·빈 쿼리플랜 캐시 상태라, **동일 코드(V1b)로**
콜드 RPS 220.9 / p99 4,867ms, 웜 RPS 454.4 / p99 475.8ms 이 나왔다. 3배 차이다.
초기에 워밍업 없이 잰 지연 수치는 전부 폐기하고 재측정했다. 지금 표의 값은 모두 2,000 요청 워밍업 후의 값이다.
(유실률은 콜드/웜 무관하게 재현됐다 — 89.92% vs 90.14%.)

그 외 한계:

- **각 변형 1회 측정**이다. 유실률과 RPS 배수처럼 차이가 큰 항목은 결론을 바꿀 여지가 없지만,
  p99 같은 꼬리 지표는 반복 측정이 필요하다.
- **비로그인 요청마다 WARN 로그가 1줄씩 쌓인다.** `AuthUserInfoResolver` 가 Authorization 헤더가 없으면
  경고를 남긴다. 모든 변형에 동일하게 적용되므로 상대 비교는 유효하지만, 절대 지연 수치를 외부에 인용하면 안 된다.
- **로컬 Docker 환경**이다. 운영 인스턴스 사양·네트워크와 다르므로 절대값이 아니라 변형 간 비교로만 읽어야 한다.

# 최초 1회: 측정 대상 행을 심고 배관 확인 (증가분이 정확히 10이어야 한다)

### 하네스에서 함께 고친 것

측정을 시작하려면 먼저 부하테스트 환경이 뜨게 만들어야 했다. 발견해 고친 것들:

- **시나리오가 존재하지 않는 경로를 호출**하고 있었다 (`/api/clubs/{id}/introduction`, 실제는 `/{clubId}/content`).
  `CLUB_ID` 기본값도 UUID 가 아닌 `1` 이었다.
- **`docker-compose.yml` 이 빈 볼륨에서 기동 불가**였다. `db/migration` 에 `clubs`/`users` 의 CREATE TABLE 이 없고
  V0 부터 ALTER 로 시작해서, Flyway 를 켜면 첫 마이그레이션에서 실패한다. ddl-auto=update 로 전환했다.
- **`application-loadtest.yml` 만으로는 기동 불가**였다 (jwt/aws/mail 등 누락 → `jwt.secret` 미해결로 죽는다).
  해당 값들은 gitignored 인 `application-dev.yml` 에만 있고 커밋할 수 없으므로 `dev,loadtest` 로 프로파일을 겹쳐 쓴다.
  > 주의: `application-dev.yml` 의 datasource 는 **로컬 DB**를 가리킨다. 컨테이너가 로컬 DB 로 가지 않는 것은
  > compose 의 `SPRING_DATASOURCE_URL` 오버라이드 덕분이다. 이 프로파일 조합으로 앱을 로컬에서 직접 실행하면
  > 로컬 DB 에 붙으니 주의할 것.
- **헬스체크가 영구히 실패**했다. `/actuator/health` 는 `SecurityWhiteList` 에 없어 401 을 돌려주므로
  컨테이너가 healthy 가 되지 못하고, `depends_on` 이 걸린 nginx 가 기동하지 않았다. 공개 엔드포인트로 교체했다.
- **`run-loadtest.ps1` 이 실행 불가**였다 (시나리오 파일명 조립 불일치, `/app` 마운트 누락,
  `BASE_URL` 기본값이 k6 컨테이너 자신을 가리킴, 결과 경로 이중 중첩).
- db 호스트 포트를 55432 로 옮겼다. 로컬 PostgreSQL 이 5432 를 점유한 환경에서 기동 실패를 피한다.

검증 범위를 분명히 해두면, 이번 측정에 실제로 사용한 경로는 `measure-viewcount.ps1` 이고 전 구간을 반복 실행했다.
`run-loadtest.ps1` 은 문법 파싱과 시나리오 해석·오류 경로까지만 확인했고 k6 전 구간을 태우지는 않았다
(모니터링 스택까지 기동해야 하는데 이번 측정에는 쓰지 않았다).
