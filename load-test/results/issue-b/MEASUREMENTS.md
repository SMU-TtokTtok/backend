작성일: 2026-10-06. 각 후보·부하·동시성 조합을 3회 + 추가 2회, 총 5회 측정했다.

**선택: V1(UNIQUE + 지정 제약 충돌 409).** 개선 후보 V1~V3의 90개 실행 모두 중복 그룹·예상 밖 HTTP 오류가 0건이었다.

## 해석과 선택

V1(UNIQUE + 지정 제약 충돌 409)을 기본안으로 선택한다. 정합성은 DB 제약으로 보장하고 애플리케이션 잠금을 추가하지 않는다.

V2는 사용자 전체를 잠그므로 같은 사용자의 다른 모집폼 지원까지 직렬화한다. V3는 사용자·모집폼으로 범위를 줄이지만 PostgreSQL 전용 SQL과 잠금 획득 쿼리가 추가된다. 두 후보는 DB UNIQUE 충돌 전에 대기시켜 불필요한 조립·저장을 줄일 수 있다.

이번 결과에는 반복 시점에 따른 큰 변동이 있다. JVM 예열·실행 순서·OS/DB 캐시·호스트 자원 변화의 영향이 가능하지만 분리해서 측정하지 않았다. 워밍업 10배치로 정상 상태에 도달했는지는 확인하지 못했다. 후보 사이에 Gradle 작업이 모두 최신 상태인데도 약 56분 대기한 비정상 실행도 있었으며 원인은 확인하지 못했다. 이 빌드 시간은 HTTP 측정 수치에 포함되지 않는다. 따라서 성능 배수나 최대 처리량을 일반화하지 않으며, 추가 잠금의 이득을 입증한 결과로 사용하지 않는다.

잠금 후보가 특정 hot 표본에서 더 빨라도 정상 지원 비용·운영 복잡성을 함께 고려한다. 실제 운영에서 충돌 빈도와 저장 비용이 높다는 관찰이 생기면 예열 안정화·실행 순서 교차·운영과 같은 파일 작업을 포함한 재측정 후 V3 도입을 검토한다.

이번 실험은 파일 없는 동기화 배치 부하이고 외부 연동은 mock이다. S3 잔여 파일, 모집 정원 동시성, 운영 데이터 정리와 배포는 검증하지 않았다.

기존 데이터와 호환되는 두 릴리스 반영 순서는 [후속 제약 안내](../../variants/issue-b/README.md)에 있다. UNIQUE가 실제 DB에 적용되기 전에는 중복 방지가 완성되지 않는다.

공식 동작 근거: [PostgreSQL UNIQUE](https://www.postgresql.org/docs/17/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS), [행 잠금과 advisory lock](https://www.postgresql.org/docs/17/explicit-locking.html).
