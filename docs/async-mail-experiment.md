# 결과 메일 벌크 전송 — 비동기 분리 방식 비교 및 측정 방법론

관련 이슈: [#320](https://github.com/SMU-TtokTtok/backend/issues/320)

## 0. 배경 — 무엇이 문제였나

`ApplicantAdminService.sendResultMailToApplicants`(`@Transactional`) → `EmailService.sendResultMail` 루프 → `this.sendEmailAsync(...)`(`@Async protected`) 흐름에서, 메일 전송이 전부 끝날 때까지 DB 트랜잭션이 종료되지 않았다.

**근본 원인은 `@Transactional`이 아니라 "비동기가 사실은 동기로 동작"한 것.**

1. **`@Async` self-invocation 무효화(핵심)** — 같은 클래스의 메서드를 `this.`로 호출하면 Spring AOP 프록시를 우회해 `@Async`가 무시된다. 게다가 `protected`라 프록시 대상도 아니다. 결과적으로 모든 SMTP 전송이 요청(=트랜잭션) 스레드에서 **동기 실행**됐다.
2. **트랜잭션이 느린 I/O를 감쌈** — 그 결과 SMTP 전송 내내 DB 커넥션이 반납되지 않았다.

참조 패턴: `FCMService.sendNotification`은 `public @Async` + 다른 빈에서 호출이라 정상 동작한다. 이 패턴을 그대로 따른다.

## 1. 두 분리 방식 — A vs B

핵심 차이는 **"메일 전송을 언제 트리거하느냐"**.

### 방식 A — `public @Async` 배치 메서드 (채택)

```
[트랜잭션 스레드] 이메일 조회 → emailService.sendResultMail(...) 호출
                  └─ @Async라 즉시 mail- 풀 스레드로 넘기고 바로 리턴
                → 트랜잭션 커밋 (커넥션 조기 반납)
[mail- 풀 스레드] SMTP 전송 (트랜잭션 밖)
```

- 트랜잭션이 끝나기 전에 비동기 작업을 "던진다(dispatch)". 던지는 순간 스레드가 넘어가 트랜잭션 스레드는 SMTP를 기다리지 않고 즉시 커밋.
- 이론적 약점: 커밋 직전에 던지므로, 커밋 직후 롤백되면 메일이 이미 나간 뒤일 수 있음.
- **이 케이스에선 사실상 무해** — `sendResultMailToApplicants`는 순수 조회(쓰기 없음)라 롤백될 일이 거의 없음.

### 방식 B — `@TransactionalEventListener(AFTER_COMMIT)` + `@Async`

```
[트랜잭션 스레드] 이메일 조회 → publishEvent(ResultMailEvent)  // 아직 발송 안 함
                → 트랜잭션 커밋 ──┐
[mail- 풀 스레드] ← AFTER_COMMIT │ 커밋 확정 뒤에만 리스너 발동 → SMTP 전송
```

- 발송이 "커밋이 성공적으로 끝난 뒤에만" 일어남을 스프링이 보장. 롤백 시 리스너가 아예 실행되지 않음.
- 대가: 이벤트 클래스 + 리스너 추가로 코드가 늘고 흐름이 한 단계 간접화.

### 트레이드오프 요약

| 항목 | A: public @Async | B: AFTER_COMMIT 이벤트 |
| --- | --- | --- |
| 커넥션 조기 반납(핵심 목표) | ✅ 달성 | ✅ 달성 |
| 커밋 성공 후에만 발송 보장 | ❌ (던진 뒤 롤백 시 메일 나감) | ✅ 보장 |
| 코드 복잡도 | 낮음 (기존 FCM 패턴 그대로) | 조금 높음 (이벤트+리스너) |
| 이 프로젝트 적합성 | 조회 전용이라 충분 | 발송 전 상태 변경(쓰기)이 생기면 안전 |

**결정: 방식 A.** (1) 현재 로직이 순수 조회라 A의 유일한 약점이 실질적으로 발생하지 않고, (2) `FCMService`라는 동일 패턴이 이미 있어 일관성·학습 비용 면에서 유리.
→ 향후 "메일 보내기 전에 지원자 상태를 '발송완료'로 변경" 같은 쓰기 로직이 생기면 그땐 B로 전환한다.

## 2. 트랜잭션은 왜 없애지 않고 `readOnly`로?

조회 코드가 지연 로딩에 의존한다. `filterApplicantsByStatus`는 `applicant.getDocumentPhase().getStatus()`, `applicant.getInterviewPhase().getStatus()` 등 연관 엔티티를 조회 도중 접근하는데, 지연 로딩이면 영속성 컨텍스트(열린 세션)가 살아 있어야 하고 그 세션은 트랜잭션 경계 안에서 보장된다. 트랜잭션을 완전히 제거하면 `LazyInitializationException` 위험.

- **트랜잭션은 필요** → 조회 중 세션 유지.
- **쓰기는 전혀 없음** → `readOnly = true`로 선언. 하이버네이트 더티 체킹 생략(성능/메모리 이득), 읽기 전용 힌트, 의도 명시.

즉 트랜잭션을 없애는 게 아니라 **범위를 짧고 읽기 전용으로 좁히는 것**이 핵심. 느린 SMTP는 async로 트랜잭션 밖으로 빠지고, 트랜잭션은 조회만 하고 즉시 끝난다.

## 3. 스레드풀 — 값의 근거

`AsyncConfig`가 비어 있어 기본 `SimpleAsyncTaskExecutor`(풀이 아니라 요청마다 새 스레드를 무제한 생성)를 쓰고 있었다. `@Async`는 전역 설정이라 FCM도 같은 executor를 공유 → 몰리면 무제한 증가 가능. 유계 풀로 격리한다.

메일은 CPU가 아닌 네트워크 I/O 대기 위주 작업. 코어 수가 아니라 "SMTP가 감당 가능한 동시 연결 수"와 "순간 부하" 기준.

| 파라미터 | 값 | 근거 |
| --- | --- | --- |
| corePoolSize | 2 | 배치가 pass/fail 2개라 평상시 충분 |
| maxPoolSize | 5 | 외부 SMTP 동시 연결 제한 → 작게 유지가 안전 |
| queueCapacity | 100 | 포화 시 버퍼. 큐가 차기 전엔 max까지 안 늘어나는 스프링 특성 유의 |
| threadNamePrefix | `mail-` | 로그·스레드 덤프 추적 및 FCM과 격리 |
| RejectedExecutionHandler | CallerRunsPolicy | 포화 시 호출 스레드가 대신 실행(백프레셔) → 메일 유실 방지 |

값은 실제 SMTP 제한·트래픽을 보고 조정한다.

## 4. A/B를 수치로 비교하려면 — 측정 방법론

성능 지표만 재면 **A와 B는 동률**로 나온다(같은 풀·같은 SMTP). 두 방식이 갈라지는 지점은 성능이 아니라 "롤백 시 행동"이며, 이는 **실패를 주입해야만** 드러난다. 그래서 측정을 두 층으로 나눈다.

### 실험 변수

- 구현 방식: `현재(동기)` / `A` / `B`
- 배치 크기 N: 10 / 100 / 500 (pass+fail 혼합)
- 통제변수 — SMTP 1통당 지연: fake SMTP(GreenMail/MailHog)에 고정 지연(예: 200ms). **이걸 상수로 박아야** 나머지가 신호가 된다. 실제 Gmail로 재면 지터가 모든 신호를 덮는다.

### 층 1 — "고쳤나?" (현재 vs A vs B, A·B 동률 예상)

| 지표 | 재는 법 (현재 actuator 미도입 → 로깅 기반) | 기대 |
| --- | --- | --- |
| **트랜잭션 유지 시간** (headline) | tx 메서드 진입/종료 시각 로깅 | 현재: `N×SMTP지연`에 선형 → 고친 뒤: 조회시간(수십 ms) 고정 |
| API 응답시간 p50/p95/p99 | 컨트롤러 로그 또는 부하도구(k6/JMeter) | N에 무관하게 평탄 |
| HikariCP active/pending peak | actuator 도입 시 `hikaricp.connections.*` | 현재 고갈 위험, 고친 뒤 안정 |
| 엔드포인트 처리량 req/s | 부하도구 | pool 고갈 전 한계 상승 |

독립변수는 배치 크기 N. "현재는 선형으로 나빠지고 A·B는 평탄"이 헤드라인 그래프.

### 층 2 — A vs B를 실제로 가르는 곳 (실패 주입)

커밋 직후 강제 예외로 롤백시키고 fake SMTP 수신함을 카운트한다.

| 지표 | A | B |
| --- | --- | --- |
| **롤백 후 발송된 메일 수** ⭐ | > 0 (이미 던진 뒤) | 0 (리스너 미발동) |
| 커밋~첫 발송 간격 | ~0 or 직전 | 커밋 후 +α |
| 신규 클래스 수 | 0 | 2 (이벤트+리스너) |

⭐ 이 한 칸이 A/B 의사결정의 실질적 전부. 층 1 전체는 "그 결정을 성능 손해 없이 내릴 수 있다"의 근거.

### 실험 위생

- 워밍업 라운드(JIT·풀 예열) 제외, 각 셀 ≥5회 반복 후 중앙값.
- fake SMTP 지연을 방식마다 동일하게 고정.
- 한 번에 한 프로파일만 기동(A/B가 같은 executor 공유 시 상호간섭).

### 결론

수치로 승부를 내는 게 아니라, **층 1로 "고쳤다"를 증명(A·B 동률 예상)하고 층 2로 "성능은 같고 안전성만 다르다"를 확인한 뒤, 최종 결정은 안전성+복잡도로 내린다.** 본 이슈에서는 위 분석에 근거해 방식 A를 구현했고, 층 1의 핵심(발송이 호출 스레드가 아닌 `mail-` 풀에서 실행됨)은 `MailAsyncDispatchTest`로 검증한다. actuator + k6 + GreenMail 기반 정량 벤치마크는 스테이징 환경에서 본 방법론대로 별도 수행한다.

## 부록 — 향후 개선 후보

- actuator + micrometer 도입 시 `hikaricp.connections.usage` 히스토그램으로 커넥션 점유시간을 상시 관측.
- 발송 실패 재시도/데드레터(현재는 로그만 남기고 유실).
- 방식 B 전환 트리거: "발송 전 지원자 상태 쓰기"가 추가되는 시점.
